Site Banner APIs with Redis

Cache site banner configurations in Redis to eliminate repeated database queries. Learn the cache-aside pattern, cache invalidation, and admin APIs for managing banners.

The Problem

Site banners (promotional banners, announcements, alerts) are displayed on every page but change infrequently. Without caching, every page load hits the database — unnecessary load for mostly-static data.

Without caching:

100,000 daily page views → 100,000 DB queries for banner data that changes once a day. Redis eliminates this with a single cache key.

Cache-Aside Pattern

Request: GET /api/banners │ ▼ Check Redis: GET banners:active │ ┌────┴────┐ │ │ HIT ✓ MISS ✗ │ │ │ ▼ │ Query database │ SET banners:active <data> EX 3600 (cache for 1 hour) │ │ └────┬────┘ ▼ Return banner data to client

This is the cache-aside (lazy loading) pattern: populate the cache only on a miss. The cache acts as a read-through layer.

Implementation (Express + Prisma + ioredis)

import { Redis } from 'ioredis';
import { PrismaClient } from '@prisma/client';
import express from 'express';

const redis = new Redis();
const prisma = new PrismaClient();
const router = express.Router();

const BANNER_CACHE_KEY = 'banners:active';
const BANNER_TTL = 3600; // 1 hour

// ── GET /api/banners ──
router.get('/banners', async (req, res) => {
  // 1. Try cache first
  const cached = await redis.get(BANNER_CACHE_KEY);
  if (cached) {
    return res.json({ data: JSON.parse(cached), source: 'cache' });
  }

  // 2. Cache miss — query DB
  const banners = await prisma.banner.findMany({
    where: { isActive: true, startDate: { lte: new Date() }, endDate: { gte: new Date() } },
    orderBy: { priority: 'desc' },
  });

  // 3. Store in cache
  await redis.setex(BANNER_CACHE_KEY, BANNER_TTL, JSON.stringify(banners));

  res.json({ data: banners, source: 'db' });
});

// ── POST /api/admin/banners ── (create)
router.post('/admin/banners', async (req, res) => {
  const banner = await prisma.banner.create({ data: req.body });
  await redis.del(BANNER_CACHE_KEY); // invalidate cache
  res.status(201).json(banner);
});

// ── PATCH /api/admin/banners/:id ── (update)
router.patch('/admin/banners/:id', async (req, res) => {
  const banner = await prisma.banner.update({
    where: { id: req.params.id },
    data: req.body,
  });
  await redis.del(BANNER_CACHE_KEY); // invalidate cache
  res.json(banner);
});

// ── DELETE /api/admin/banners/:id ──
router.delete('/admin/banners/:id', async (req, res) => {
  await prisma.banner.delete({ where: { id: req.params.id } });
  await redis.del(BANNER_CACHE_KEY); // invalidate cache
  res.status(204).send();
});

Cache Invalidation Strategies

1. Delete on Write (used above)

Delete the cache key whenever data changes. Next read repopulates it. Simple but causes a brief cache miss spike on high-traffic sites.

2. Write-Through

// Update DB AND cache simultaneously
await Promise.all([
  prisma.banner.update({ where: { id }, data }),
  redis.setex(BANNER_CACHE_KEY, BANNER_TTL, JSON.stringify(updatedBanners)),
]);

3. TTL Expiry Only (for low-stakes data)

Let the cache expire naturally. Acceptable when a 1-hour stale banner is fine. No invalidation code needed.

Which to use?

For banners: Delete on write is the right choice. Banners change rarely (maybe once a day), so a cache miss after each admin update is negligible.

Redis Data Structure Choice

JSON String (simple approach)

// Store entire list as a single JSON string
await redis.setex('banners:active', 3600, JSON.stringify(banners));
const cached = JSON.parse(await redis.get('banners:active') || '[]');

Hash (granular, per-banner)

// Store each banner as a hash field
for (const banner of banners) {
  await redis.hset('banners', banner.id, JSON.stringify(banner));
  await redis.expire('banners', 3600);
}

// Get all banners
const all = await redis.hgetall('banners');
const banners = Object.values(all).map(v => JSON.parse(v));

// Get single banner without fetching all
const one = JSON.parse(await redis.hget('banners', bannerId) || 'null');
Recommendation:

For banners, a single JSON string key is simpler and usually sufficient. Use Hash when you need to update individual banners without invalidating the entire cache.

Cache Key Naming Convention

banners:active              → all currently active banners
banners:homepage            → banners specific to homepage
banners:category:electronics → category-specific banners
banners:user:premium        → banners for premium users

# Admin-specific (longer TTL or no cache)
admin:banners:all           → all banners including inactive

Use colon-separated namespaces for Redis keys. Makes it easy to use SCAN with patterns and delete related keys: redis.keys('banners:*').
