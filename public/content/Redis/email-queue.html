Email Queue with Redis

Decouple email sending from your request cycle using Redis Lists as a simple, reliable job queue. Process emails asynchronously without blocking user requests.

The Problem

Sending emails synchronously in the request handler blocks the user's response and makes your app vulnerable to email provider outages. The solution: queue the job and process it in the background.

Don't do this:

API request → send email → wait → respond. If the email provider is slow, every user waits. If it's down, the entire request fails.

Do this instead:

API request → push job to Redis queue → respond immediately → background worker picks up job → sends email.

Architecture

HTTP Request (POST /register) │ ▼ API Server - Create user in DB - LPUSH email:queue '{"to":"user@example.com","template":"welcome"}' ──→ Redis List - Return 201 Created (fast!) │ ┌───────────────────┘ ▼ Email Worker (separate process) - BRPOP email:queue (blocking) - Parse job - Call Nodemailer / SendGrid - Log result - Loop

Redis List as a Queue

# FIFO Queue pattern:
# - Producer: LPUSH (push to head)
# - Consumer: BRPOP (blocking pop from tail)

# Producer
LPUSH email:queue '{"to":"alice@example.com","subject":"Welcome","template":"welcome"}'
LPUSH email:queue '{"to":"bob@example.com","subject":"Reset","template":"reset_password"}'

# Consumer (blocking — waits up to 30s for a job)
BRPOP email:queue 30
# Returns: 1) "email:queue"  2) '{"to":"alice@example.com",...}'

# Check queue depth
LLEN email:queue    # → 2

# Peek without consuming
LRANGE email:queue 0 4   # show first 5 items
BRPOP vs RPOP:

BRPOP blocks the connection until a job arrives (up to the timeout). This avoids busy-polling and is more CPU-efficient than repeatedly calling RPOP in a loop.

Producer (API Server)

import Redis from 'ioredis';
import nodemailer from 'nodemailer';

const redis = new Redis();

interface EmailJob {
  to: string;
  subject: string;
  template: 'welcome' | 'reset_password' | 'order_confirm';
  data?: Record<string, unknown>;
}

export async function queueEmail(job: EmailJob): Promise {
  await redis.lpush('email:queue', JSON.stringify(job));
  console.log(`Email queued for: ${job.to}`);
}

Worker Process

import Redis from 'ioredis';

const redis = new Redis();

async function processEmail(job: EmailJob): Promise {
  // Use Nodemailer, SendGrid, AWS SES, etc.
  const transporter = nodemailer.createTransport({ /* config */ });
  await transporter.sendMail({
    to: job.to,
    subject: job.subject,
    html: renderTemplate(job.template, job.data),
  });
  console.log(`Email sent to ${job.to}`);
}

async function runWorker(): Promise {
  console.log('Email worker started. Waiting for jobs...');

  while (true) {
    try {
      // Block for up to 30 seconds waiting for a job
      const result = await redis.brpop('email:queue', 30);

      if (!result) continue; // timeout, loop again

      const [, rawJob] = result;
      const job: EmailJob = JSON.parse(rawJob);

      await processEmail(job);
    } catch (err) {
      console.error('Error processing email job:', err);
      // Optional: push to a dead-letter queue for inspection
      // await redis.lpush('email:failed', rawJob);
      await new Promise(r => setTimeout(r, 1000)); // brief backoff
    }
  }
}

runWorker();

Dead-Letter Queue (Failed Jobs)

// In the worker error handler:
const MAX_RETRIES = 3;

async function processWithRetry(rawJob: string): Promise {
  const job = JSON.parse(rawJob);
  const retries = job._retries || 0;

  try {
    await processEmail(job);
  } catch (err) {
    if (retries < MAX_RETRIES) {
      job._retries = retries + 1;
      // Re-queue with retry count (RPUSH = lower priority, processed later)
      await redis.rpush('email:queue', JSON.stringify(job));
      console.log(`Retrying job (attempt ${job._retries})`);
    } else {
      // Give up — move to dead-letter queue for manual inspection
      await redis.lpush('email:dead', rawJob);
      console.error(`Job failed after ${MAX_RETRIES} retries. Moved to dead-letter queue.`);
    }
  }
}
Upgrade path:

For production workloads, switch from raw Redis Lists to BullMQ. It gives you retries, delays, prioritization, concurrency, and a dashboard — all built on Redis.

Key Takeaways

  • Use LPUSH to enqueue, BRPOP to dequeue (FIFO).
  • Keep job payloads as small as possible — store just enough to process the task.
  • Run the worker as a separate process (pm2, Docker service, etc.).
  • Monitor queue depth with LLEN email:queue — alert if it grows unexpectedly.
  • Use a dead-letter queue to catch failed jobs for debugging.
