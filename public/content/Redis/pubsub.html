How Pub/Sub Works

Redis Pub/Sub implements the observer pattern at the infrastructure level. Publishers send messages to named channels. Subscribers listen to channels and receive messages in real time.

Publisher A ──→ PUBLISH notifications "{'type':'new_order'}" ──→ Redis Channel: notifications Publisher B ──→ PUBLISH notifications "{'type':'payment'}" ──→ Redis Channel: notifications │ ┌──────────────────────────┘ ▼ Subscriber 1 (email service) Subscriber 2 (analytics service) Subscriber 3 (push notification service)
Fire-and-forget:

Redis Pub/Sub is not a message queue. If a subscriber is offline when a message is published, it misses that message. Use Redis Streams or BullMQ when you need guaranteed delivery.

Core Commands

CommandRoleDescription
SUBSCRIBE channelSubscriberListen to a specific channel
PSUBSCRIBE patternSubscriberListen using glob pattern (e.g. user:*)
PUBLISH channel messagePublisherSend message to all channel subscribers
UNSUBSCRIBE channelSubscriberStop listening to a channel
PUBSUB CHANNELSAdminList active channels with at least 1 subscriber
PUBSUB NUMSUB channelAdminNumber of subscribers on a channel

CLI Example

# Terminal 1 — Subscriber
redis-cli
SUBSCRIBE notifications
# Reading messages...  (blocks here)

# Terminal 2 — Publisher
redis-cli
PUBLISH notifications '{"type":"new_order","orderId":"ORD-123"}'
# (integer) 1  ← number of subscribers that received it

# Terminal 1 will print:
# 1) "message"
# 2) "notifications"
# 3) "{\"type\":\"new_order\",\"orderId\":\"ORD-123\"}"

Node.js Implementation

Important:

A connection in SUBSCRIBE mode can only run Pub/Sub commands. Create separate Redis connections for publishing and subscribing.

import Redis from 'ioredis';

const publisher = new Redis();
const subscriber = new Redis();

// ── Subscriber ──
await subscriber.subscribe('notifications', 'alerts');

subscriber.on('message', (channel, message) => {
  console.log(`Channel: ${channel}`);
  const payload = JSON.parse(message);

  if (channel === 'notifications') handleNotification(payload);
  if (channel === 'alerts') handleAlert(payload);
});

// ── Pattern Subscriber ──
await subscriber.psubscribe('user:*');

subscriber.on('pmessage', (pattern, channel, message) => {
  console.log(`Pattern: ${pattern}, Channel: ${channel}`);
  // channel might be "user:123:orders" or "user:456:profile"
});

// ── Publisher ──
async function publishOrderEvent(orderId: string) {
  const payload = JSON.stringify({ type: 'new_order', orderId, timestamp: Date.now() });
  const receiverCount = await publisher.publish('notifications', payload);
  console.log(`Message delivered to ${receiverCount} subscriber(s)`);
}

Common Use Cases

🔔 Real-time Notifications

Push order updates, payment confirmations, or alert events to multiple services simultaneously.

💬 Chat Systems

Broadcast messages in a chat room to all connected users on the same channel.

📊 Live Dashboards

Push metrics updates to monitoring dashboards without polling.

🔄 Cache Invalidation

Notify all app instances to invalidate a cached key when the source data changes.

🎮 Game Events

Broadcast game state changes (score updates, player actions) to all participants.

🔗 Microservice Events

Decouple services — emit events on channels instead of direct API calls.

Pub/Sub vs Streams vs BullMQ

FeaturePub/SubStreamsBullMQ
Message persistence❌ No✅ Yes✅ Yes
Replay missed messages❌ No✅ Yes❌ No
Job retry on failure❌ NoPartial✅ Yes
Fan-out (1 → many)✅ YesPartial❌ No
ComplexityLowMediumMedium
Best forReal-time broadcastsEvent sourcingJob queues
Rule of thumb:

Use Pub/Sub for ephemeral broadcasts where it's OK to miss messages. Use BullMQ or Streams when delivery must be guaranteed.
