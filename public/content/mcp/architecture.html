Section 01

The Simplest MCP Architecture

The architecture of MCP begins with just two entities. Everything else is built on top of this foundation. Starting from first principles, detail is gradually added throughout the video.

🤖

Host

The AI chatbot that users interact with. The user types a prompt → the Host receives it → sends it to an LLM (OpenAI, Anthropic, Gemini, etc.). This is the interface layer — could be Claude Desktop, Cursor IDE, or a custom-built chatbot.

🔧

Server

A tool/service with the capability to execute a specific task. Examples: a GitHub server to manage repositories, a Slack server to read/write messages, or a Google Drive server to manipulate files. Servers do the actual work.

Simplest Flow: User asks "Are there any new commits on the GitHub repo?" → Host receives prompt → sends to LLM → LLM realises it can't answer from training data → LLM says "Ask the GitHub server" → Host queries the server → server returns latest commits → LLM formats the answer → user sees the response.

Section 02

Introducing the MCP Client

In reality, the Host never communicates directly with the Server. Communication always passes through a helper entity called the MCP Client. This is the key architectural refinement over the simplified view.

Key Insight: The MCP Client is the entity that speaks the MCP language fluently. Because the client knows the MCP protocol, it can communicate seamlessly with any MCP-compliant server. The Host just hands off a high-level request to the client; the client handles all protocol-level communication.
🤖

Host

The AI chatbot/application. Receives user prompts, invokes the LLM, decides WHEN a tool needs to be called. Generates high-level requests. Never speaks directly to servers.

🔌

MCP Client

The protocol translator and communication handler. Lives inside the Host. Converts high-level requests into MCP-format messages, sends them to servers, and translates responses back for the Host to understand.

⚙️

MCP Server

The actual capability/tool. GitHub, Slack, Google Drive, File System, etc. Speaks MCP natively. Receives structured requests, executes tasks, returns structured responses. Does all the heavy lifting.

Section 04

One-on-One Relationship & The SIM Card Analogy

A crucial rule in MCP: the Client-Server relationship is always one-on-one. One client can only communicate with one server at a time. If a Host needs to talk to multiple servers, it needs one separate client per server.

// Diagram: One-on-one client-server relationships — one client per server

The SIM Card Analogy

MCP Architecture

  • Host = Your phone (the intelligence)
  • MCP Client = SIM card (protocol handler)
  • MCP Server = Mobile network (Airtel/Jio)
  • Multiple servers = Install multiple SIM cards
  • 1:1 rule = Each SIM connects to one network

Phone Analogy

  • Phone doesn't talk to the tower directly
  • SIM translates for the phone
  • Tower (network) does the heavy work
  • Multi-SIM phone = multiple independent channels
  • Each SIM-to-network link is independent and 1:1
Section 05

Architecture Benefits

🔗

Decoupling (Separation of Concerns)

Each client-server communication channel is isolated. The GitHub channel knows nothing about the Slack channel. If the GitHub connection fails, Slack and Drive connections keep working perfectly. This creates fault isolation and operational safety.

📈

Scalability

Want to add a new server? Just add one more client inside the Host. The pattern is consistent and infinitely extensible. One Host can theoretically connect to hundreds of servers simultaneously — each through its own dedicated client.

⚡

Parallelism

Because each server has a separate client, multiple tool calls can execute simultaneously. If a task requires both GitHub data AND Slack messages, both can be fetched in parallel — not sequentially. This dramatically speeds up complex tasks.

🛡️

Security Isolation

Each client maintains its own credentials and auth tokens for its server. Security is scoped per-connection. A vulnerability in one integration doesn't automatically expose credentials for other integrations.

Section 06

MCP Primitives — What Servers Offer to Hosts

Primitives are the three types of offerings that a Server can provide to a Host. Understanding these is essential to understanding what you can do with any MCP server.

Definition: Primitives are things the server can offer to the host. Every MCP server exposes its capabilities through exactly these three primitives — Tools, Resources, and Prompts.
Primitive Type Definition Nature GitHub Example Google Drive Example
tools/ 🔧 Actions Things the AI can ASK the server to DO. Executable actions that perform real operations. Dynamic — changes over time Count commits, list issues, create PR, push code Create file, search documents, upload files
resources/ 📄 Data Structured data sources the AI can READ. Static knowledge documents on the server. Static — doesn't change frequently README.md content, repository description Database schema, configuration document
prompts/ 📝 Templates Predefined prompt templates that guide HOW the AI should use the server. Behavioral instructions. Instructional — shapes AI behavior GitHub Issue Report template with required fields Document formatting guidelines

The Prompts Primitive — Detailed Example

Prompts are the trickiest to understand. Here's how the concept is explained with a concrete scenario:

❌ Without Prompt Primitive

User asks to "create an issue for a bug: the login button doesn't work."


The LLM generates a vague issue:


Title: "Login bug"
Body: "The login button doesn't work."


❌ Lacks steps to reproduce, expected behavior, environment details — useless for developers.

✓ With Prompt Primitive

Server stores a template: "Always include: Title, Steps to Reproduce, Expected Behavior, Actual Behavior, Environment."


The LLM reads this template and generates:


Title: "Login button bug"
Steps: 1. Open login page 2. Enter credentials 3. Click login
Expected: User logged in
Actual: Nothing happens
Env: Chrome, macOS

When to use Prompts: Not needed in every scenario. They're useful in specialised cases where you want to enforce a specific format or quality standard on how the AI interacts with a particular server. Think of them as "server usage guidelines" for the AI.

Section 08

Data Layer — JSON-RPC 2.0 Explained

The Data Layer is the language and grammar of the MCP ecosystem. It defines exactly how Client and Server messages are structured — the rules both sides follow to communicate.

Definition: The Data Layer is the language and grammar of the MCP ecosystem that everyone agrees upon to communicate. In MCP, this grammar is provided by JSON-RPC 2.0.

What is JSON-RPC?

RPC — Remote Procedure Call

A mechanism that allows a program to execute a function on another computer as if it were local — hiding all the network details. Instead of writing complex API calls, you simply say "call this function with these parameters" and the result comes back.


// Instead of this:
fetch("https://server/add", {method:"POST",...})

// RPC lets you write this:
rpc.call("add", [2, 3]) // → 5

JSON-RPC = RPC + JSON Format

JSON-RPC combines the RPC concept with the simplicity of JSON. All RPC requests and responses are structured as standard JSON objects, making them easy to write, read, and debug.


Currently on version 2.0 — hence the full name JSON-RPC 2.0. This is the version MCP uses as its data layer foundation.

Section 09

JSON-RPC Message Examples

Let's see exactly how MCP communication looks in JSON-RPC 2.0 format. These are real message structures used when clients talk to servers.

Example 1: tools/list — Discover available tools

When an AI chatbot first connects to a GitHub server, the first thing it does is ask: "What can you do for me?"

→ CLIENT REQUEST

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {}  // No params needed
}

← SERVER RESPONSE

{
  "jsonrpc": "2.0",
  "id": 1,  // Same ID — matches request
  "result": {
    "tools": [
      { "name": "list_issues",
        "description": "List all open issues" },
      { "name": "list_pulls",
        "description": "List all pull requests" }
    ]
  }
}

Example 2: tools/call — Execute a specific tool

→ CLIENT REQUEST

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "list_issues",
    "arguments": {
      "owner": "demo-user",
      "repo": "mcp-demo"
    }
  }
}

← SERVER RESPONSE

{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "issues": [
      { "id": 1, "title": "Login bug",
        "state": "open" },
      { "id": 2, "title": "UI fix",
        "state": "open" }
    ]
  }
}

Example 3: Error Response

→ CLIENT sends malformed request (missing repo)

{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "list_issues",
    "arguments": {
      "owner": "demo-user"
      // Missing: "repo" field!
    }
  }
}

← SERVER returns structured error

{
  "jsonrpc": "2.0",
  "id": 3,  // ID matches — client knows which req failed
  "error": {
    "code": -32602,  // Invalid params error code
    "message": "Missing required field: repo"
  }
}
The ID field is critical: Every JSON-RPC request includes an id. Every response echoes back that same id. This is how the client matches responses to requests — especially important when multiple requests are sent simultaneously. The client can tell "this response belongs to request #3."
Section 10

Notifications & Batching in JSON-RPC

Notifications — Fire and Forget

Regular Request/Response

Every request MUST get a response. Client sends request → server MUST reply. Used when you need data back. Identified by the presence of an id field.


Client: "What are the issues?" → Server: "Here they are: [...]"

Notifications

No response expected. Either side can send a notification; the recipient just acknowledges it internally. Identified by the absence of an id field. Think: "fire and forget."


Server: "Hey, README.md was updated!" → Client just records this, no reply needed.

// Notification from Server → Client (no id field!)
{
  "jsonrpc": "2.0",
  // No "id" field — this is a notification, not a request
  "method": "notifications/resources/updated",
  "params": {
    "uri": "github://demo-user/mcp-demo/README.md",
    "updated_by": "user",
    "updated_at": "2025-04-20T10:30:00Z"
  }
}
// Client receives this because it subscribed via resources/subscribe

Batching — Multiple Requests in One

JSON-RPC allows sending multiple requests in a single array. Useful when you need data from multiple tools simultaneously — reduces round trips.

// Batch request: fetch issues AND pull requests at once
[
  {
    "jsonrpc": "2.0", "id": 1,
    "method": "tools/call",
    "params": { "name": "list_issues", "arguments": { "repo": "mcp-demo" } }
  },
  {
    "jsonrpc": "2.0", "id": 2,
    "method": "tools/call",
    "params": { "name": "list_pulls", "arguments": { "repo": "mcp-demo" } }
  }
]
// Server returns both results in a single batch response array
Section 11

Why JSON-RPC over REST API? (5 Reasons)

REST API could theoretically do the same job (fetching data from remote machines). Here is exactly why Anthropic chose JSON-RPC 2.0 instead — and why this choice was architecturally brilliant.

01
Lightweight Protocol

REST uses HTTP which adds many headers, metadata, and overhead to every request. JSON-RPC messages are just plain JSON — no headers, no HTTP verbs (GET/POST/PUT), no overhead. Easier to write, easier to debug, faster to transmit between machines.

02
Supports Bidirectional Communication

REST is inherently one-way: client requests, server responds. In JSON-RPC, the server can also send requests to the client. This is crucial for MCP — servers need to push notifications to clients when data changes, which REST can't natively do.

03
Transport Agnostic

REST is tied to HTTP. JSON-RPC works over ANY transport: stdio, HTTP, WebSockets, custom transports. This lets MCP use different transports for local vs remote servers (stdio for local, HTTP+SSE for remote) while keeping the same message format.

04
Supports Request Batching

REST requires a separate HTTP call for each request. JSON-RPC lets you bundle multiple requests into a single transmission. In AI workflows, it's common to need data from multiple tools simultaneously — batching makes this efficient.

05
Built-in Notifications (Fire & Forget)

REST has no concept of one-way messages that don't need a response. JSON-RPC natively supports notifications. When a server needs to inform clients about changes (like a subscribed resource being updated), notifications are the perfect mechanism.

Section 12

Transport Layer — Local vs Remote Servers

The Transport Layer is the mechanism that physically moves JSON-RPC messages between Client and Server. The transport mechanism depends on where the server lives — local machine or remote internet.

Definition: The Transport Layer is the mechanism that moves JSON-RPC messages between the client and server. It's the "pipe" through which messages flow — the physical medium, not the message format (that's JSON-RPC's job).
💻

Local Servers

A server running on the SAME machine as the Host. Installed on the user's computer. Example: a File System MCP server that reads/writes local files. Has access to local resources that a remote server could never reach.


Transport: stdio (Standard Input/Output)

🌐

Remote Servers

A server running on a DIFFERENT machine — on the internet or a company network. Example: GitHub's MCP server running on GitHub's infrastructure. Accessible from anywhere on the internet.


Transport: HTTP + SSE (Server-Sent Events)

stdio Transport — How Local Server Communication Works

For local servers, MCP uses stdio (Standard Input/Output) — the fundamental I/O mechanism built into every programming language. This is elegant, fast, and secure.

stdio basics: Every running program has two built-in communication channels: stdin (standard input — receives data from outside) and stdout (standard output — sends data to outside). In normal programming, stdin = keyboard input and stdout = screen output.

⚡

Extremely Fast

Both processes are on the same machine. No network latency. Literally two processes piping data directly to each other through the OS — as fast as it gets.

🔒

Maximum Security

No network ports opened. No internet exposure. Communication is entirely within the machine's process boundaries. Zero attack surface from the network.

🛠️

Simple to Implement

Every programming language (Python, JavaScript, Java, C++, Go) has built-in stdio support. Writing an MCP server that uses stdio requires minimal boilerplate code.

Demo Proof — Hello.py Analogy

Key insight: When you run python3 hello.py in a terminal and type a name when prompted, you're already doing all 3 stdio steps: (1) Terminal launches Python as a subprocess, (2) Your keyboard input goes via stdin, (3) "Hello World!" appears via stdout. This is EXACTLY how Claude Desktop communicates with local MCP servers — just with JSON-RPC messages instead of names.
Section 14

HTTP + SSE Transport — Remote Servers

For remote servers (running on the internet), MCP uses HTTP for sending requests and Server-Sent Events (SSE) for receiving streaming responses.

HTTP — The Request Mechanism

🌐HTTP is the most universal application protocol on the internet — the host can reach any server globally using it.
📦Client sends an HTTP POST request to the server's URL with a JSON body containing the JSON-RPC message.
🔑All standard HTTP authentication methods work: Bearer tokens, API keys in headers, OAuth — no new auth system needed.
✅Well understood, well documented, supported by every language and framework. Widely deployed infrastructure.

SSE — The Streaming Response Mechanism

🔄SSE = Server-Sent Events. An HTTP extension that allows a server to push multiple messages over a single open connection.
📺Instead of waiting for one big JSON response, the server streams data chunk by chunk as it becomes available — creating the "typing" effect in AI.
⏱️Ideal for long-running tasks and incremental updates — common in AI agents that perform multi-step workflows.
🔌Single open connection maintained — server can push updates to client whenever new data is ready without waiting for a new request.
// HTTP POST request carrying JSON-RPC payload to remote MCP server
POST https://api.github-mcp.com/mcp
Content-Type: application/json
Authorization: Bearer YOUR_GITHUB_TOKEN

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "list_repositories",
    "arguments": { "sort": "stars", "limit": 5 }
  }
}

// Server responds via SSE — streams results as they're ready
data: {"jsonrpc":"2.0","id":1,"result":{"repos":[{"name":"repo1"...}

// Connection stays open for follow-up streaming updates

Section 16

Key Takeaways — Complete Architecture Summary

🏗️ Architecture Components

Host — The AI chatbot (Claude Desktop, Cursor, custom). Contains LLM + multiple clients.

MCP Client — One per server. The protocol translator inside the Host. Handles all low-level MCP communication.

MCP Server — The tool/capability (GitHub, Slack, FileSystem). Does all the heavy lifting. Can be local or remote.

⚖️ Relationship Rules

One-on-One — Each client ↔ exactly one server.

Host → Client — Host never talks to server directly.

Parallel — Multiple clients run independently and can execute simultaneously.

Scale — Add unlimited servers by adding one client per server.

📦 Three Primitives

Tools — Dynamic actions (execute tasks). Use: tools/list + tools/call

Resources — Static data (read documents). Use: resources/list + resources/read + subscribe/unsubscribe

Prompts — Behavioral templates (guide AI). Use: prompts/list + prompts/get

🔌 Two Transport Modes

stdio — For local servers (same machine). Fast, secure, no network. Host launches server as subprocess; communicates via stdin/stdout pipes.

HTTP + SSE — For remote servers (internet). Uses HTTP POST for requests, SSE for streaming responses. Works with all standard HTTP auth.

The Elegant Insight — Data Layer + Transport Layer Separation: JSON-RPC handles WHAT messages say (data format). Transport handles HOW messages travel (the pipe). By separating these two concerns, MCP achieves transport agnosticism — the same JSON-RPC message format works identically whether sent via stdio to a local server or via HTTP to a remote server. This architectural decision makes MCP flexible, extensible, and future-proof.
