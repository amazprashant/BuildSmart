Section 01

What is the MCP Lifecycle?

Definition: The MCP Lifecycle describes the complete sequence of steps that govern how a Host and a Server establish, use, and end a connection during a session. It is the rulebook that the entire MCP architecture follows during runtime.

What is a Session?

A session is one continuous, uninterrupted connection between a client and a server — from the moment the client connects to the moment the connection is terminated.

🖥️

Example: Claude Desktop + GitHub Server

When you start Claude Desktop, it automatically connects to your configured GitHub MCP server behind the scenes. The connection persists until you close Claude Desktop. That entire duration — from launch to close — is one session.

📋

Why Does the Lifecycle Matter?

The lifecycle defines the order in which things must happen. Do them in the wrong order and the system crashes. This video explains exactly what happens step by step in every session — knowledge essential for building your own MCP servers and clients.

Section 02

The Three Phases Overview

🤝

Phase 1 — Initialization

Client and server meet for the first time. They exchange capabilities, negotiate protocol versions, and confirm the connection is ready. Like a handshake before starting work.

⚡

Phase 2 — Operation

The main working phase. Client discovers exact tools/resources, then sends task requests. Server executes and responds. All the actual work happens here.

🔌

Phase 3 — Shutdown

The session is deliberately terminated. Typically initiated by the client. No JSON-RPC messages are exchanged — the transport layer handles it entirely.

Section 03
1
Phase 1 — Initialization

The MCP spec explicitly states: "The initialization phase MUST be the first interaction between client and server." Two goals: (1) protocol version compatibility check, (2) capabilities exchange.

The 3 Steps of Initialization

01
Client → Server: "initialize" request

Client fires a JSON-RPC request with method "initialize". Includes: (a) its MCP protocol version, (b) its capabilities (roots, sampling, elicitation), (c) its implementation info (name and version).

02
Server → Client: initialize response

Server replies with same three pieces from its side: (a) its MCP protocol version, (b) what it offers (tools, resources, prompts, logging), (c) its implementation info (server name and version).

03
Client → Server: "initialized" notification — session confirmed

Client sends a notification (no ID — fire and forget) called "notifications/initialized". No reply needed. Once server receives this, the session is LIVE and normal operations begin.

Actual JSON-RPC Messages (from the live demo)

→ STEP 1: Client initialize request

{
  "jsonrpc": "2.0", "id": 0,
  "method": "initialize",
  "params": {
    "protocolVersion": "2024-11-05",
    "capabilities": {
      "roots": { "listChanged": true },
      "sampling": {}
    },
    "clientInfo": {
      "name": "Claude AI",
      "version": "0.7.5"
    }
  }
}

← STEP 2: Server response

{
  "jsonrpc": "2.0", "id": 0,
  "result": {
    "protocolVersion": "2024-10-07",
    "capabilities": {
      "tools": { "listChanged": true }
    },
    "serverInfo": {
      "name": "Secure Filesystem Server",
      "version": "2.0.0"
    }
  }
}

→ STEP 3: Initialized notification (no id — no reply needed)

{
  "jsonrpc": "2.0",
  // No "id" — this is a notification. Server does NOT reply.
  "method": "notifications/initialized"
}
// Server receives this → session is LIVE → normal operations can begin

Section 05

Two Critical Initialization Rules

🚫

Rule 1 — Client Side

Client MUST NOT send any requests (other than pings) before the server has responded to the initialize request.

No tool calls, no lists — nothing until Step 2 completes. Only ping is the exception.

🚫

Rule 2 — Server Side

Server MUST NOT serve any requests (other than pings and logging) before receiving the "initialized" notification.

Server stays silent until Step 3 is confirmed. Can send pings and log messages only.

Summary: Until all 3 initialization steps complete, both parties are restricted to pings (and logging for server only). This protects system integrity — processing requests mid-handshake risks crashes and inconsistent state.
Section 06

Version Negotiation

MCP continuously evolves — different versions exist. During initialization, both parties share their protocol version. When they differ, the client checks compatibility.

// Version negotiation decision flowchart
Real observation: Claude Desktop sent version "2024-11-05" and the Filesystem server responded "2024-10-07". Different versions — but Claude supports "2024-10-07" in its compatibility list, so the session proceeded. Version negotiation doesn't require exact match, just compatibility.
Section 07

Capability Negotiation — What Clients Offer

The client declares what it can offer to the server. Three main client capabilities:

CapabilityNameWhat it MeansExample
rootsDirectory Access Client grants server access to its base directory structure. Server can work with files in those folders. Cursor IDE grants its project folder to a Filesystem server so the server can create/edit files in the project.
samplingAI Sampling If the server needs AI inference, it can ask the client to run it using the client's own LLM. Server delegates AI tasks back to the client. Server asked to summarize 1000 docs. Instead of its own AI, it asks client: "Run your LLM on these docs and give me summaries."
elicitationIncomplete Info Request Server can ask the client for missing information it needs to complete a task mid-session. Client asks server to fetch GitHub repos but forgot the API key. Server replies: "I also need your API key to connect."
Sub-capabilities: Capabilities have sub-capabilities too. roots has listChanged — when true, the server is notified if the client's root list changes. tools has listChanged to notify when tools are added/removed during the session.
Section 08

Capability Negotiation — What Servers Offer

🔧

tools

Executable actions (functions) the client can call. Each tool has a name, description, and input schema. Example: create_issue, read_file.

📄

resources

Static documents/data sources the client can read. Non-dynamic: README files, database schemas, config documents.

📝

prompts

Pre-defined prompt templates that guide the AI on how to use the server correctly for specialised workflows.

📋

logging

Server can emit structured log messages to the client. During long tasks, server sends progress logs so the user can track what's happening.

Note: Announcing a capability is just step one — it tells the client WHAT TYPES of capabilities exist. The exact list of specific tools/resources/prompts is discovered in the next phase (Operation — Capability Discovery).
Section 09
2
Phase 2 — Operation

The main working phase. Two rules: (1) Respect the negotiated protocol version in all messages. (2) Only use capabilities that were successfully negotiated during initialization.

Part A: Capability Discovery (Automatic)

Immediately after initialization, the client automatically sends batch requests to discover exact tools/resources/prompts available:

// Three discovery requests sent automatically as a batch
[
  { "jsonrpc":"2.0", "id":1, "method":"tools/list" },
  { "jsonrpc":"2.0", "id":2, "method":"prompts/list" },
  { "jsonrpc":"2.0", "id":3, "method":"resources/list" }
]
// Filesystem server responds with full tool list for id:1
// Returns "Method not found" errors for id:2 and id:3 (server has no prompts/resources)
// Host stores tool list → LLM uses it to route user queries to right tools

Part B: Tool Calls (User-Driven)

Once the client has the full tools list, for every user query the LLM identifies the needed tool and the client calls it:

// User: "What's written in hello.py on my Desktop?"
// LLM identifies: use read_file tool
{ "jsonrpc":"2.0", "id":5, "method":"tools/call",
  "params": { "name":"read_file", "arguments": { "path":"/Desktop/hello.py" } } }

// Server reads the file and responds:
{ "jsonrpc":"2.0", "id":5, "result": {
    "content": [{ "type":"text", "text":"name = input('Enter name:')\nprint(f'Hello {name}')" }]
} }

Section 11
3
Phase 3 — Shutdown

The session is terminated. No JSON-RPC messages are exchanged — confirmed by the live demo which showed only "Server Transport Closed" in logs, with zero JSON-RPC messages. The transport layer handles everything.

Shutdown for Local Servers (stdio)

Client-Initiated (Most Common)

Step 1: Client closes server's stdin stream
Step 2: Waits for server process to exit gracefully
Step 3: Sends SIGTERM if server doesn't exit ("please exit politely")
Step 4: Sends SIGKILL if still alive ("exit NOW — forced")

Server-Initiated (Rare)

Server closes its stdout stream
Server process exits on its own
Client detects disconnected pipe
Client cleans up pending requests

Shutdown for Remote Servers (HTTP)

Client-Initiated (Normal)

Client closes the HTTP POST connection it had with the server. The TCP socket is released. Clean and simple.

Server-Initiated (Unexpected)

Server closes the HTTP connection from its end. Client must handle this gracefully — stop pending tasks, potentially retry, inform the user what happened.

SIGTERM vs SIGKILL: SIGTERM = "Please finish up and leave" (server can clean up state). SIGKILL = "Exit immediately — forced by OS." Always try SIGTERM first; SIGKILL is the last resort.
Section 12 — Special Case

Special Case: Pings (Heartbeat Checks)

🏓Pings — Checking if the Other Side is Alive

A ping is a lightweight request-response method to check if the connection is still alive and responsive. Both client and server can send pings to each other.

→ PING REQUEST

{
  "jsonrpc": "2.0",
  "id": 42,       // Has ID — expects reply
  "method": "ping"
}

← PING RESPONSE

{
  "jsonrpc": "2.0",
  "id": 42,       // Same ID — confirmed alive
  "result": {}   // Empty — just "I'm here"
}

When Are Pings Used?

During Initialization

Pings are one of only two allowed messages during initialization before the handshake completes. Used to test if the connection path is open.

Long-Running Tasks

If no messages have been exchanged for a while, periodic pings keep the connection alive and prevent OS/firewall from silently closing the idle connection.

Connection Keepalive

Pings tell the OS/proxy: "This connection is still active." Without them, idle connections can be silently terminated by firewalls or proxy servers.

Section 13 — Special Case

Special Case: Error Handling

⚠️Error Handling — JSON-RPC Standard

MCP directly inherits JSON-RPC 2.0's error handling standard. The error object structure is identical to any JSON-RPC distributed system.

Standard Error Object

{
  "jsonrpc": "2.0",
  "id": 3,              // Matches the failed request
  "error": {
    "code": -32601,    // Standard error code
    "message": "Method not found",
    "data": {          // Optional debugging info
      "details": "Server does not support prompts capability"
    }
  }
}

Error Scenarios & Standard Error Codes

CodeNameMeaning
-32700Parse ErrorInvalid JSON received — message cannot be parsed at all.
-32600Invalid RequestValid JSON but doesn't conform to JSON-RPC 2.0 spec. Missing required fields.
-32601Method Not FoundCalled method (e.g., prompts/list) doesn't exist on server. Most common error!
-32602Invalid ParamsTool called with wrong/missing/extra arguments.
-32603Internal ErrorServer crashed or hit unexpected state while processing the request.
-32000 to -32099Server ErrorAuth failures, rate limits, quota exceeded, timeout, etc.

Common Error Scenarios

Version mismatch

Protocol version incompatibility during initialization — connection immediately terminated.

Unknown method called

Client calls a method never negotiated (e.g., prompts/list from a tools-only server).

Invalid arguments

Tool called with wrong types, missing required fields, or extra unknown fields.

Server crash

Server encountered an unexpected error while processing — internal server failure.

Timeout exceeded

Client's configured wait time elapsed. Client cancels request, frees resources.

Malformed JSON-RPC

Syntax error in the message, missing required JSON-RPC fields, not valid JSON.

Section 14 — Special Case

Special Case: Timeouts & Request Cancellation

⏱️Timeouts — Don't Wait Forever

A timeout is a maximum wait duration set by the client per request. If the server doesn't respond within that time, the client cancels to avoid the user waiting indefinitely.

🚫

Prevent Infinite Waiting

Without timeouts, a user could wait hours for an overloaded/crashed server. Timeouts give timely feedback that something went wrong.

💾

Free Resources

Pending requests consume memory and CPU. Timeouts trigger resource cleanup, freeing the system for other tasks.

📢

User Feedback

User gets an explicit error message instead of seeing a spinner indefinitely. They can retry or check if server is down.

How Timeout Works — Step by Step

01
Client configures a timeout per-request in MCP SDK

Example: "Wait maximum 30 seconds for this request."

02
Client sends request and starts a countdown timer

Request dispatched normally. If server responds within timeout, all is well.

03
Timer expires → Timeout triggered → Cancellation notification sent

Client automatically fires a cancellation notification to the server.

04
Server stops processing, sends no response

On receiving cancellation, server halts work on that request. Request abandoned on both sides.

Cancellation Notification Message

// Timer expired for request id:7 (scan entire codebase)
// Client sends cancellation notification:
{
  "jsonrpc": "2.0",
  // No "id" — this is a notification
  "method": "notifications/cancelled",
  "params": {
    "requestId": 7,
    "reason": "Timeout exceeded: 30 seconds"
  }
}
// Server immediately stops processing request #7
Section 15 — Special Case

Special Case: Progress Notifications

📊Progress Notifications — Real-Time Updates

For long-running tasks, servers can send periodic progress updates. This powers real-time progress bars — like ChatGPT's Deep Research progress indicator.

Purpose: Let the client know a long-running request is still making progress — so the user doesn't assume the system is frozen and cancel prematurely.

How Progress Notifications Work

1. Client adds a progressToken

When making a long-task request, the client adds a unique progressToken in the request's _meta field. This token links all progress updates to this specific request.

2. Server sends periodic updates

As it processes, the server sends notifications/progress notifications referencing the progress token — showing how much work is done out of total.

Full Progress Example — Scanning a Codebase for Vulnerabilities

// Step 1: Client request with progressToken
{
  "jsonrpc":"2.0", "id":9, "method":"tools/call",
  "params": {
    "name":"search_code",
    "arguments": { "repo":"my-app", "pattern":"security_vulnerability" },
    "_meta": { "progressToken":"token-7" }
  }
}

// Step 2: Server sends periodic progress notifications (no id — no reply needed)
{ "method":"notifications/progress", "params":{
    "progressToken":"token-7", "progress":25, "total":100,
    "message":"Scanning 250 of 1000 files..."
}}
{ "method":"notifications/progress", "params":{
    "progressToken":"token-7", "progress":60, "total":100,
    "message":"Scanning 600 of 1000 files..."
}}
{ "method":"notifications/progress", "params":{
    "progressToken":"token-7", "progress":100, "total":100,
    "message":"Scan complete!"
}}

// Step 3: Server sends the actual final result
{ "jsonrpc":"2.0", "id":9, "result":{ "vulnerabilities":["..."] }}
Real-world analogy: ChatGPT's Deep Research shows a progress bar: "30% research complete... 60%... 90%... Done." That UX is powered by the same concept — underlying agent sends progress notifications rendered as a progress bar for the user.

Final Summary

🤝 Initialization

3 steps: request → response → notification. Version check in middle. No other messages allowed until all 3 complete. Capabilities exchanged.

⚡ Operation

Auto-discovery first (tools/list batch). Then user-driven tool calls (tools/call). Uses only negotiated capabilities. Core work happens here.

🔌 Shutdown

Transport layer only — NO JSON-RPC. stdio: close stdin → SIGTERM → SIGKILL. HTTP: close TCP. Client typically initiates shutdown.

🎯 Special Cases

Pings (keepalive), Errors (JSON-RPC codes), Timeouts (cancellation notifications), Progress (streaming updates for long tasks).
