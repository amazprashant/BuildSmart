Microservices vs Monolith

🧱 Monolith

  • Single deployable unit
  • Simple to develop and test locally
  • Easy to debug — one process
  • Scales as a whole (wasteful)
  • Technology lock-in
  • One bug can take down everything
  • Best for: startups, MVPs, small teams
VS

🔀 Microservices

  • Independent services per domain
  • Deploy, scale, and fail independently
  • Distributed tracing required
  • Scale bottleneck services only
  • Polyglot — different language per service
  • Network calls replace function calls
  • Best for: large teams, complex domains

⚠ The Distributed Systems Tax

Microservices introduce: network latency between services, distributed transactions (hard!), service discovery complexity, and the need for observability tools (tracing, metrics, logs aggregation). Don't start with microservices — migrate when your monolith actually hits limits.

Service Communication Patterns

🔗

Synchronous (HTTP/gRPC)

Service A calls Service B and waits for response. Simple but coupling — if B is down, A fails too.

📨

Asynchronous (Events)

Service A publishes an event. Service B processes when ready. Decoupled but harder to debug.

🔄

Service Mesh

Sidecar proxies (Istio/Envoy) handle retries, mTLS, circuit breaking, and observability automatically.

API Design

REST

  • HTTP verbs + resources
  • Stateless, cacheable
  • Over/under-fetching
  • Human readable (JSON)
  • Widely supported
  • Best for: public APIs

GraphQL

  • Single endpoint, typed schema
  • Client specifies exact fields
  • No over/under-fetching
  • Complex queries in one request
  • Harder caching
  • Best for: complex client data needs

gRPC

  • Binary protocol (Protocol Buffers)
  • 10x faster than REST/JSON
  • Bi-directional streaming
  • Strong typing + codegen
  • Not browser-native
  • Best for: internal microservices

API Gateway Pattern

An API Gateway sits in front of all microservices and handles: authentication (verify JWT once, not in every service), rate limiting, request routing, SSL termination, request/response transformation, and observability. Tools: Kong, AWS API Gateway, Nginx.

Message Queues & Event-Driven Architecture

Message queues decouple producers (who create work) from consumers (who process it). The queue buffers messages when consumers can't keep up, enabling async processing and absorbing traffic spikes.

Queue vs Stream

FeatureQueue (RabbitMQ / BullMQ)Stream (Kafka)

Replay messages❌ No✅ Yes — seek to offset

Key Concepts

✅

Acknowledgement

Consumer tells the queue "I processed this successfully." On failure, message is requeued.

💀

Dead Letter Queue

Messages that fail N times go to DLQ for inspection. Prevents poison messages from blocking queues.

🔄

Idempotency

Processing the same message twice must produce the same result. Use unique IDs to detect duplicates.

🔢

Consumer Groups

Multiple consumers share the load of a queue. Scale consumers independently from producers.

Rate Limiting

Rate limiting protects APIs from abuse, ensures fair usage, and prevents overload. Every public API should have it.

Rate Limiting Algorithms
Token Bucket
🪣
Bucket holds N tokens.
Each request consumes 1 token.
Tokens replenish at fixed rate.
Allows bursts up to bucket size.
✓ Handles traffic bursts
Fixed Window Counter
🪟
Count requests in each time window (e.g., 1 min).
Reset counter at window edge.
Simple, but vulnerable to boundary bursts.
⚠ Boundary burst problem
Sliding Window Log
📜
Track timestamp of each request in a sorted set.
Count requests in the last N seconds.
No boundary issues. High memory cost.
✓ Accurate, no bursts
Sliding Window Counter
🔢
Estimate using current + previous window counters.
Low memory. Slightly approximate.
Best of both worlds.
✓ Recommended for production

Implementing with Redis

// Sliding window counter with Redis
async function isRateLimited(userId: string, limit = 100, windowMs = 60000): Promise<boolean> {
  const key = `rl:${userId}`;
  const now = Date.now();
  const windowStart = now - windowMs;

  const pipeline = redis.pipeline();
  pipeline.zremrangebyscore(key, 0, windowStart);   // remove old timestamps
  pipeline.zadd(key, now, `${now}`);                // add current request
  pipeline.zcard(key);                              // count in window
  pipeline.expire(key, Math.ceil(windowMs / 1000));
  const results = await pipeline.exec();

  const count = results![2][1] as number;
  return count > limit;
}

Consistent Hashing

🔄

The Problem

In simple modulo sharding (key % N servers), adding or removing a server remaps nearly all keys — causing a massive cache miss storm. Consistent hashing solves this by minimising remapping.

Consistent Hash Ring

Keys are hashed and placed on the ring. Each key maps to the next server clockwise. Adding/removing a server only remaps ~1/N keys.

Used in: CDNs, Distributed Caches, DHTs

Consistent hashing is the backbone of systems like Amazon DynamoDB, Apache Cassandra, Memcached clusters, and Akamai CDN. It enables efficient horizontal scaling of distributed storage with minimal data movement when the cluster changes.

Case Study: Design a URL Shortener

URL shortener (like bit.ly or TinyURL) is a classic system design interview question. Let's design it end-to-end.

Step 1 — Requirements

Functional

  • Given a long URL, return a short code
  • Redirect short URL to original
  • Custom aliases (optional)
  • Link expiry (optional)
  • Click analytics

Non-Functional (Scale)

  • 100M URLs created per day
  • 10:1 read/write ratio
  • <10ms redirect latency (p99)
  • 99.99% availability
  • 5-year URL storage

Step 2 — Back-of-Envelope Estimates

# Writes
100M URLs/day = 100M / 86,400 ≈ 1,160 QPS write

# Reads (10:1 ratio)
1M redirect requests/day  = 11,600 QPS read (peak ~3x = 35,000 QPS)

# Storage
Each URL record ≈ 500 bytes
100M/day × 365 × 5 years = 182.5 billion records
182.5B × 500B = ~91 TB total storage

# Short code
6 characters (Base62: a-z A-Z 0-9) = 62^6 ≈ 56.8 billion unique codes
→ More than enough for 182.5B if we use 7 chars (62^7 = 3.5 trillion)

💡 Interview Tips
  • Why not key % N for ID? → collision risk, DB dependency. Snowflake IDs are better.
  • 301 vs 302? → 301 is cached by browser, so clicks won't reach server. Use 302 if tracking is needed.
  • Custom aliases? → Store in same table with a flag; check uniqueness on insert.
  • Expiry? → TTL column in DB + background cleanup job OR Redis TTL if URL only lives in cache.

System Design Checklist

📋 Always Ask

  • What is the scale? (DAU, QPS, data size)
  • Read-heavy or write-heavy?
  • Consistency vs availability trade-off?
  • Latency requirements (SLA)?
  • Global or single region?
  • Any existing tech constraints?

🏗 Always Consider

  • Load balancing (single point of failure?)
  • Caching (where, what, how long?)
  • Database choice + sharding strategy
  • Async processing for heavy tasks
  • CDN for static assets
  • Monitoring, alerting, observability

⚠ Common Pitfalls

  • Designing for day-1 scale you don't have
  • Forgetting failure scenarios
  • No cache invalidation strategy
  • Ignoring the network (latency, timeouts)
  • Over-engineering with microservices too early

🛠 Key Tools

  • LB: Nginx, HAProxy, AWS ALB
  • Cache: Redis, Memcached
  • Queue: Kafka, RabbitMQ, SQS, BullMQ
  • DB: Postgres, MySQL, Cassandra, DynamoDB
  • CDN: Cloudflare, CloudFront, Akamai
