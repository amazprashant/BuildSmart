What is System Design?

💡

Core Definition

System design is the process of defining the architecture, components, modules, interfaces, and data flow of a system to satisfy specific functional and non-functional requirements. It answers: how will this system work at scale?

⚡

Performance

How fast does the system respond? Latency, throughput, and response times under load.

🏔

Scalability

Can the system handle 10x more users? Horizontal and vertical growth strategies.

✅

Reliability

Will it keep working even when parts fail? Fault tolerance and graceful degradation.

🛡

Availability

What percentage of time is the system up? 99.9% = 8.7 hrs/yr downtime.

🔧

Maintainability

Can new engineers understand and modify the system? Clear abstractions, good docs.

🔒

Security

Is data protected? Authentication, authorization, encryption, and audit trails.

System Design Interview Framework

1

Clarify Requirements

Ask about scale (DAU, QPS), features (must-have vs nice-to-have), and constraints (latency SLAs, budget). Never jump to design without this.

2

Estimate Scale

Back-of-envelope calculations: storage, bandwidth, QPS. Example: 1M DAU × 10 requests = 10M requests/day ≈ 115 QPS.

3

High-Level Design

Sketch boxes and arrows. Client → API layer → services → databases. Identify core components first.

4

Deep Dive

Zoom into the most critical or interesting components. Discuss data models, APIs, algorithms, and trade-offs.

5

Address Bottlenecks

Where does the system break? Add caches, sharding, replication, CDNs. Discuss failure modes and recovery.

2

Scalability

Scalability is the system's ability to handle increased load without degrading performance. There are two fundamental approaches:

⬆ Vertical Scaling (Scale Up)

  • Add more CPU, RAM, or storage to existing server
  • Simple — no code changes required
  • Hard limit: largest available machine
  • Single point of failure remains
  • Downtime required for hardware upgrades
  • Best for: databases, quick wins
VS

↔ Horizontal Scaling (Scale Out)

  • Add more machines to the pool
  • Requires stateless services or shared state
  • Theoretically unlimited scale
  • No single point of failure
  • Zero-downtime scaling
  • Best for: web servers, microservices

Layer 4 vs Layer 7 Load Balancing

L4 (Transport layer): Routes based on IP + TCP/UDP port only. Fast, no content inspection. Good for raw throughput.

L7 (Application layer): Routes based on HTTP headers, URL paths, cookies. Enables path-based routing (/api/* → API servers, /static/* → CDN). More powerful, slightly more overhead.

Cache Hit vs Miss

A cache hit returns data from cache (fast, ~1ms). A cache miss fetches from the source (slow, ~100ms), then stores in cache for next time. Aim for 80%+ hit rate.

Cache Strategies

🔵 Cache-Aside (Lazy)

App checks cache first. On miss, reads DB and writes to cache. Most common pattern.

✍ Write-Through

Write to cache AND DB simultaneously. Cache always fresh, but write latency increases.

📋 Write-Back (Write-Behind)

Write to cache only, async to DB later. Fastest writes, risk of data loss on crash.

🔄 Read-Through

Cache sits in front of DB. On miss, cache fetches and stores. App only talks to cache.

⚠ Cache Invalidation — the hard problem

Phil Karlton famously said: "There are only two hard things in Computer Science: cache invalidation and naming things." When data changes, you must decide: delete cache key immediately, update it, or let TTL expire it. Each choice has trade-offs between consistency and complexity.

5

CAP Theorem

In a distributed system, you can only guarantee two of three properties simultaneously. This is the CAP Theorem, proven by Eric Brewer.

C — Consistency

Every read receives the most recent write or an error. All nodes see the same data at the same time.

A — Availability

Every request receives a response (not necessarily the latest data). System stays operational even if some nodes fail.

P — Partition Tolerance

System continues operating even if network packets are dropped between nodes. In real distributed systems, P is always required.

Practical implication

Since network partitions will happen in any distributed system, P is non-negotiable. The real choice is: when a partition occurs, do you sacrifice Consistency (AP — return possibly stale data) or Availability (CP — return an error)?

Database Design & Scaling

🗂 SQL (Relational)

  • Structured schema, ACID guarantees
  • Strong consistency
  • Complex joins and queries
  • Vertical scaling primary
  • PostgreSQL, MySQL, SQLite
VS

📦 NoSQL

  • Flexible/schema-less data models
  • Eventual consistency (usually)
  • Optimised for specific access patterns
  • Horizontal scaling built-in
  • MongoDB, Cassandra, DynamoDB, Redis

⚠ Sharding trade-offs

Sharding eliminates the single-database bottleneck but adds complexity: cross-shard queries become hard, resharding requires data migration, and joins across shards are expensive. Choose your shard key carefully — user ID, geography, or tenant ID are common choices.

Availability = (Uptime / Total time) × 100

Most production SLAs target 99.9% (three nines). Achieving five nines requires active-active multi-region deployments, zero-downtime deploys, and automated failover — it's expensive and complex.

🔄 MTTR — Mean Time To Recover

How quickly can the system recover from failure? Lower is better. Improve with runbooks, automated alerts, and on-call rotations.

⏱ MTBF — Mean Time Between Failures

How long does the system run before failing? Higher is better. Improve with better hardware, testing, and redundancy.
